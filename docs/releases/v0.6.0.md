**Logs you can filter, and actions that ask before they act.** A structured
log line now renders as `time LEVEL message │ k=v` and can be narrowed by text
or by severity floor. Lens actions gained parameters — values collected in a
form with typeahead suggestions drawn from the cluster's own state — which is
what turns "fence an instance" from a free-text box into a list of the
instances that exist, and what makes restoring a CloudNativePG cluster
expressible at all.

## Log lines, parsed ([#10](https://github.com/0x01001011/k10s/pull/10))

JSON and logfmt records render as `time LEVEL message │ k=v`, with the record's
own timestamp dropped where it duplicates the stream's. `f` filters live
(`-term` excludes), `w` cycles the level floor (all → INFO → WARN → ERROR), and
`t` shows the raw lines again for the moment the parse is the thing you doubt.

## Actions can ask ([#11](https://github.com/0x01001011/k10s/pull/11))

A lens action may declare `params`: values collected before it runs, each a
field with suggestions filtered as you type.

```yaml
params:
  - name: instance
    required: true
    optionsFrom: .status.instanceNames
```

`optionsFrom` takes two shapes, told apart by the leading dot a JSONPath always
has and a GVR never does. `.status.instanceNames` reads a list — or a map's
sorted keys — off the object. `postgresql.cnpg.io/v1/backups` lists related
objects of that kind, resolved through the pack's **existing** `edges`: "which
Backups belong to this Cluster" was already declared there for the relationship
panel, and the restore form reads the same statement rather than a second
query language invented for it.

Everything resolves in `internal/k8s`. The UI never parses a JSONPath, never
touches a lister, and never sees an unrendered template — it draws what it is
given, which is the division the rest of the lens surface already keeps.

`confirmValue` makes the typed gate ask for the value at risk. Fencing acts on
an *instance*, so making the operator type the *cluster's* name confirms
something they were never shown.

The command preview recomputes on every keystroke. It is there to be checked
against, so one that lags the field it describes is a preview of a different
mutation.

## CloudNativePG, as a day-2 console

Fence and promote pick from `.status.instanceNames` with the primary marked.
Promote now carries the guard `kubectl cnpg promote` applies before patching:
it refuses while the cluster holds a fencing annotation, because a fenced
instance has no running Postgres to promote and the patch would set
`targetPrimary` and then sit in `Switchover in progress` with nothing on screen
to explain it.

Backup takes `method` and `target`. `Backup.spec` is immutable after creation,
so a wrong method cannot be corrected afterwards — only deleted and recreated —
which is why both are chosen up front rather than left to be fixed.

**Restore** creates a *new* Cluster with a `bootstrap.recovery` stanza and an
optional recovery time. CloudNativePG never restores in place, which is the
most surprising thing about it for anyone arriving from a traditional Postgres
setup, so the notice says so rather than leaving it to be discovered by an
operator who reached for "restore" expecting the broken cluster to be repaired.

Two new columns carry what an SRE actually checks. **`WAL`** reads the
`ContinuousArchiving` condition and grades `False` as an error — the failure
worth building a column for, because when WAL archiving breaks *nothing else on
the row changes*. The cluster keeps reporting `Cluster in healthy state` while
the recovery window stops advancing and `pg_wal` grows until the volume fills.
Every backup taken since is a lie. **`NODES`** is `.status.topology.nodesUsed`:
what `cnpg_collector_nodes_used` measures, without needing Prometheus.

Four new kinds — Databases, Publications, Subscriptions, Image Catalogs — the
declarative CRDs CloudNativePG shipped from 1.25 on. Each grades
`applied: false` as an error, because it means the object exists and the
database change did not happen.

## Fixed

A create action's confirm modal used to paint its manifest over the panes
behind it. The kubectl equivalent of a create is a heredoc — several lines in
one string — and the modal neither split it nor reserved rows for it. Fixed in
the renderer every confirm modal shares, rather than at the one call site that
happened to show it.

CloudNativePG Poolers now grade against `active | paused | inactive | failed`.
The pack named `"Pooler is ready"`, a string the operator never writes, so the
table matched nothing and every healthy PgBouncer rendered amber indefinitely.
The mistake was copying the shape of `Cluster.status.phase`, which *is* a human
sentence, onto a field that is not one.

## Smaller

- A lens kind's tenth action is reachable as `0`. CloudNativePG has exactly ten
  verbs and the numbering stopped at nine, so hibernating a cluster had a key
  and waking it did not — a trap rather than a limitation.
- A parameter default is rendered as a template, so `"{{.Name}}-restore"`
  reaches the form as `orders-db-restore` instead of arriving with its braces
  intact.
- A `create` body drops empty fields before it is sent. An unset recovery
  target used to be written as an empty one, which CloudNativePG has to
  interpret and which leaves the cluster never finishing bootstrap. `annotate`
  is deliberately not pruned — there the empty string is how un-fencing removes
  a key.
- The demo has fixtures for every CloudNativePG kind. One cluster reports
  healthy with a dead WAL archive, which is how it looks in production.

## Next

`NODES` is ungraded on purpose. Severity tables map a *value*, and whether
`nodesUsed: 1` is bad depends on `INSTANCES` — one node is correct for a
single-instance cluster and wrong for a three-instance one. Grading it would
paint every dev cluster amber forever, which is the mistake this release fixes
in `pooler-phase`. It needs a schema that can express a comparison.

`requiresSelection` survives for argocd, kargo and longhorn. Parameters replace
it and retiring it is the right end state, but that is three packs and their
tests, so it is its own change.

Replica-cluster promotion is still not offered. It needs
`.spec.replica.promotionToken`, whose value comes from the *other* cluster's
`.status.demotionToken` — possibly in another kubeconfig context — and a
token-less promotion silently degrades into a failover that forces a rebuild of
the former primary. It should not be one keypress until that token can be
sourced safely.
